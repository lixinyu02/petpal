# 工作台流畅性与 UI 优化

- Date: 2026-09-30
- Complexity: L1
- Status: implementing

## Background

用户要求进一步优化 UI 流畅性，并评估 Rust 重写。现有 App 的每个 Chat delta 更新完整页面状态；口型的高频播放状态使历史列表与消息行反复协调；消息引用变化无条件滚到底部。Markdown 正文已有 memo，但不能隔离消息列表、历史按钮和页面状态更新。

## Goal and design

- 视觉主张：延续奶油白与低饱和绿，以消息内容和输入区为主，减少重复说明与空白欢迎区对短屏的占用。
- 内容安排：模式与模型保持清楚，历史阅读、流式回复和执行状态分别呈现；返回最新消息采用一个按需出现的入口。
- 交互主张：回复平稳增量显示，读历史时保留当前位置，模式与菜单使用短暂轻量反馈，人物动作保持自然且遵循减少动画偏好。
- 仅合并 Chat 的显示更新，不改变共享 SSE、工具调用、语音分句或 Agent UUID/排队/审批。完成、错误、停止和账号变化处理必须保留终态与清理门禁。
- 将稳定历史消息的渲染与语音高频状态分隔；自动跟随最新回复只在用户位于底部时进行，主动发送和切换会话仍定位最新。
- 基于人物循环和资源加载审计补充可证实的低风险优化。使用 Chrome 与隔离固定回复、长历史测量前后表现，不用固定测试回复冒充真实模型验收。

## Rust decision

目前发现的是浏览器主线程 React/Markdown/滚动调度，后端大多是模型、语音服务与 CLI 的 I/O。Rust 或 Tauri 不能直接消除这些前端更新。先保留当前架构；仅在实测证明本地 CPU 运算、启动体积或内存问题仍为主要瓶颈时评估局部原生模块，避免四端与已有 CLI/设备能力的迁移成本。
